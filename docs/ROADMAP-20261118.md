## 一、项目为什么"卡了很久"：一句话版本

内核很早就跑到 kext 加载阶段了，但**每一轮都在同一个地方死掉**，而那个地方是我们自己写的诊断代码：

```
读 GICR redistributor 的 SGI 帧  →  esr 0x96000010（同步外部中止）
  →  平台错误处理器把它当"已处理"并恢复出错指令
    →  同一条读再次中止  →  无限风暴  →  面板刷屏、只能长按断电、DRAM 里的诊断全丢
```

再加上 **dts 缺 `cluster-type` 导致 8 核里只有 CPU0 真正启动**，于是"定时器不计数 / 等待超时 /
看起来卡死"这些现象全都能被解释，而它们的真正原因跟 USB、显示、AMFI 都没有关系。

## 二、问题清单

### P1 平台错误风暴（已修，待验证）

| 项 | 内容 |
|---|---|
| 现象 | 面板无限打印 `ArmDTPlatformIO: platform error #N far=… pc=… (ignored)` |
| 证据 | b261 panic：`pc 0xfffffff00c411a0c`、`esr 0x96000010`、指令 `ldr w11,[x10,#0x80]!`（`x10 = redist + 0x10000`）|
| 成因 | `ArmCpu::prepareGic()` 里我们加的 `kprintf("… igroupr0=%08x isenabler0=%08x", …)` 回读了 SGI 帧；`enableGic()` 与 `armcpu_gic_diag()` 还有同样的两处 |
| 为什么写没事读就炸 | 写是 posted（无人应答就丢弃），读必须等应答 → 外部中止 |
| 修法 | 三处回读全删/置 `0xffffffff`（b262 `abe0af7`）|
| 验收 | 面板不再出现 `platform error`；内核继续往下走 |

### P2 只有 CPU0 在跑（已修，待验证）

| 项 | 内容 |
|---|---|
| 现象 | `ArmCpu: 0 timer interrupts, 0 IPIs`；`IOServiceWait` 大量堆积；系统像卡死 |
| 证据 | 两份**工作参考**（`UniXNU-sheng` 跑 macOS、`Allenwdk/UniXNU-uke` 跑 iPadOS）的 dts 都给 8 个核标了 `unixnu,cluster-type`；他们注释写明：缺类型会退化成 SMP，`cluster_type_to_pset_type()` 在 `processor_bootstrap()` 里**拒绝**该核 |
| 注意 | `sheng-smp=1` 我们**本来就有**（`board.toml:747`），缺的只有 dts 里那 8 行 |
| 修法 | `dts/uke.dts` 加 8 行（0-2 E、3-7 P），已用 `dtc`+`make-adt.py` 验证 ADT 里是 `E/E/E/P/P/P/P/P`（b263 `c84dc9d`）|
| 验收 | **`ArmCpu: N timer interrupts` N>0**，`armcpu_smp_step[]` 出现非 0，`IOServiceWait` 不再堆积 |

### P3 内核日志通道（未修，依赖 P2）

| 项 | 内容 |
|---|---|
| 现象 | 扫 QR 只拿到固件日志；userdata 尾 32 MiB 窗口 517/33554432 字节非零（无任何 `UKELOG1`）|
| 成因 | `UkeLastLog` 的 userdata transport 要走到 BSD init 才 attach；内核死得更早 |
| 现成方法 | 参考实现就是这么读的：`sheng-log=1` + `UkeLastLog` 写 userdata 尾 32 MiB，**TWRP 下 `dd`**（`work/ref-allenwdk/docs/RECOVERY-LOG.md`；我们本地工具 `work/analysis/read-uke-log.py`）|
| 另一条已死的路 | `uke_mark` 写的 `0x9FFDFD000` 页在平台保留区，**每次启动固件都报 `no kernel boot marks`** → 该通道不可用，别再依赖 |
| 验收 | 启动日志出现 `UkeLastLog: userdata log window at lba …, 8192 blocks`，TWRP 能 dd 出 `UKELOG1` |

### P4 本地分叉（已定位，未清理）

见 `docs/UPSTREAM-REVIEW-20261118.md`。一句话：`drivers/ArmCpu` 这个本地覆盖**应该整段删掉**，
改用核心仓库的上游版本（它已含 `redistributor-stride` 解析与 `/arm-io` 基址换算，且启动路径不回读 SGI 帧）；
`drivers/ArmDTPlatform` 相反，上游没有 `handlePlatformError`，**必须保留**。

### P5 USB（另一条线，未开始验证）

| 项 | 内容 |
|---|---|
| 已知错 | repeater 调参表抄了 SM8550/sheng 的值（`{0x51,0x08},{0x54,0x03},{0x57,0x05}`），厂商 DT 里 0x54 恒为 0x02，三套序列（normal/factory/host）都对不上 |
| 正确来源 | `work/ref-vendor-dt/qcom/uke-sm8635.dtsi:2465` 的 `qcom,param-override-seq{,-factory,-host}`，**成对顺序是 (value, offset)**；我们要的是 **device 角色那列**（normal），不是 host 列 |
| 硬前置 | 刷 USB 实验轮时**必须去掉 `uke-platform-error-panic=1`**，否则开机死在 ArmCpu、到不了 stage 6/7 |
| 验收 | 面板/日志 `dctl` 的 `devctrlhlt` 由 1 变 0、`run_stop=1`、`usblnkst` 离开 0；主机 `lsusb` 出现设备 |

## 三、下一步（每轮只改一个变量）

| 轮次 | 改什么 | 怎么算成功 | 失败时先看什么 |
|---|---|---|---|
| **b263**（已推）| dts 加 8 个 `cluster-type`（含 b262 的 GIC 修复）| `N timer interrupts` **N>0** | 若仍 panic 在 ArmCpu → GIC 那处没修净；若 N 仍为 0 → 看 `armcpu_smp_fail[]`/`armcpu_smp_step[]` 的值 |
| **b264** | 删 `feeds.toml` 里 ArmCpu 的 `local`+`git` 两行，改用核心上游 ArmCpu | 行为与 b263 一致（风暴不出现、N>0），但少一个分叉 | 编译期符号缺失 → 说明我们的驱动依赖了分叉里的东西，逐条搬回 |
| **b265** | 对齐参考参数：`armcpu-self-ipi=1`（sheng 有我们没有，IPI 走 SPI 的配套开关）| IPI 计数增长、`armcpu_ipi_interrupts` 非 0 | IPI 仍为 0 → 看 GIC SPI 路由与 `armcpu-spi-ipi` |
| **b266** | 日志通道：让内核走到 BSD init 后 attach userdata transport | TWRP dd 出 `UKELOG1` 记录 | 对照 `work/ref-allenwdk/docs/RECOVERY-LOG.md` 的前置条件 |
| 之后 | 显示（`sheng-*` 参数族）、AMFI（注意 sheng 不用 `amfi_get_out_of_my_way=1`）、USB（P5）| — | — |

**为什么这个顺序**：P1/P2 决定"内核能不能继续跑"，P3 决定"我们能不能看见"，P4 决定"以后改得快不快"，
P5 是外设。先把前四个解决，后面的调试成本会直线下降（不用再拍屏、不用再猜）。

## 四、每轮的操作手册（照抄）

```bash
# 1. 推分支（一次只推一个！）
cd work/push/uke-main-merge && git checkout -b ci-bNNN-xxx && git push mine ci-bNNN-xxx

# 2. 等 CI（约 35 分钟），取产物并打镜像（约 6 分钟）
cd /home/tonghua/Code/mcOS
python3 work/round.py <RUN_ID> --name bNNN-xxx --core work/push/UniXNU \
        --device work/push/uke-main-merge --profile macos-27.3-uke

# 3. 刷（两个分区都要刷；先断电 10 秒）
bash work/flash/apply.sh bNNN-xxx

# 4. 观察（不要长按断电！）→ 进菜单 Tools → Advanced Logger 扫码，或 TWRP 下 dd userdata 尾窗口
bash work/flash/restore-os4.sh    # 实验结束回 Android
```

**判读顺序**：`ArmCpu: mapGic/wakeRedistributor failed`（GIC 映射）→ `ArmCpu: N timer interrupts`
（核/定时器）→ `ArmCpu: smp step`（从核启动）→ `AppleImage4` / `BootLocker`（kext 阶段）→ 其它 panic。
