## 一、项目为什么"卡了很久"：一句话版本

内核很早就跑到 kext 加载阶段了，但**每一轮都在同一个地方死掉**，而那个地方是我们自己写的诊断代码：

```
读 GICR redistributor 的 SGI 帧  →  esr 0x96000010（同步外部中止）
  →  平台错误处理器把它当"已处理"并恢复出错指令
    →  同一条读再次中止  →  无限风暴  →  面板刷屏、只能长按断电、DRAM 里的诊断全丢
```

再加上 **dts 缺 `cluster-type` 导致 8 核里只有 CPU0 真正启动**，于是"定时器不计数 / 等待超时 /
看起来卡死"这些现象全都能被解释，而它们的真正原因跟 USB、显示、AMFI 都没有关系。

## 二、问题清单

### P1 平台错误风暴（已修，待验证）

| 项 | 内容 |
|---|---|
| 现象 | 面板无限打印 `ArmDTPlatformIO: platform error #N far=… pc=… (ignored)` |
| 证据 | b261 panic：`pc 0xfffffff00c411a0c`、`esr 0x96000010`、指令 `ldr w11,[x10,#0x80]!`（`x10 = redist + 0x10000`）|
| 成因 | `ArmCpu::prepareGic()` 里我们加的 `kprintf("… igroupr0=%08x isenabler0=%08x", …)` 回读了 SGI 帧；`enableGic()` 与 `armcpu_gic_diag()` 还有同样的两处 |
| 为什么写没事读就炸 | 写是 posted（无人应答就丢弃），读必须等应答 → 外部中止 |
| 修法 | 三处回读全删/置 `0xffffffff`（b262 `abe0af7`）|
| 验收 | 面板不再出现 `platform error`；内核继续往下走 |

### P2 只有 CPU0 在跑（已修，待验证）

| 项 | 内容 |
|---|---|
| 现象 | `ArmCpu: 0 timer interrupts, 0 IPIs`；`IOServiceWait` 大量堆积；系统像卡死 |
| 证据 | 两份**工作参考**（`UniXNU-sheng` 跑 macOS、`Allenwdk/UniXNU-uke` 跑 iPadOS）的 dts 都给 8 个核标了 `unixnu,cluster-type`；他们注释写明：缺类型会退化成 SMP，`cluster_type_to_pset_type()` 在 `processor_bootstrap()` 里**拒绝**该核 |
| 注意 | `sheng-smp=1` 我们**本来就有**（`board.toml:747`），缺的只有 dts 里那 8 行 |
| 修法 | `dts/uke.dts` 加 8 行（0-2 E、3-7 P），已用 `dtc`+`make-adt.py` 验证 ADT 里是 `E/E/E/P/P/P/P/P`（b263 `c84dc9d`）|
| 验收 | **`ArmCpu: N timer interrupts` N>0**，`armcpu_smp_step[]` 出现非 0，`IOServiceWait` 不再堆积 |

### P3 内核日志通道（未修，依赖 P2）

| 项 | 内容 |
|---|---|
| 现象 | 扫 QR 只拿到固件日志；userdata 尾 32 MiB 窗口 517/33554432 字节非零（无任何 `UKELOG1`）|
| 成因 | `UkeLastLog` 的 userdata transport 要走到 BSD init 才 attach；内核死得更早 |
| 现成方法 | 参考实现就是这么读的：`sheng-log=1` + `UkeLastLog` 写 userdata 尾 32 MiB，**TWRP 下 `dd`**（`work/ref-allenwdk/docs/RECOVERY-LOG.md`；我们本地工具 `work/analysis/read-uke-log.py`）|
| 另一条已死的路 | `uke_mark` 写的 `0x9FFDFD000` 页在平台保留区，**每次启动固件都报 `no kernel boot marks`** → 该通道不可用，别再依赖 |
| 验收 | 启动日志出现 `UkeLastLog: userdata log window at lba …, 8192 blocks`，TWRP 能 dd 出 `UKELOG1` |

### P4 本地分叉（已定位，未清理）

见 `docs/UPSTREAM-REVIEW-20261118.md`。一句话：`drivers/ArmCpu` 这个本地覆盖**应该整段删掉**，
改用核心仓库的上游版本（它已含 `redistributor-stride` 解析与 `/arm-io` 基址换算，且启动路径不回读 SGI 帧）；
`drivers/ArmDTPlatform` 相反，上游没有 `handlePlatformError`，**必须保留**。

### P5 USB（另一条线，未开始验证）

## 四、每轮的操作手册（照抄）

```bash
# 1. 推分支（一次只推一个！）
cd work/push/uke-main-merge && git checkout -b ci-bNNN-xxx && git push mine ci-bNNN-xxx

# 2. 等 CI（约 35 分钟），取产物并打镜像（约 6 分钟）
cd /home/tonghua/Code/mcOS
python3 work/round.py <RUN_ID> --name bNNN-xxx --core work/push/UniXNU \
        --device work/push/uke-main-merge --profile macos-27.3-uke

# 3. 刷（两个分区都要刷；先断电 10 秒）
bash work/flash/apply.sh bNNN-xxx

# 4. 观察（不要长按断电！）→ 进菜单 Tools → Advanced Logger 扫码，或 TWRP 下 dd userdata 尾窗口
bash work/flash/restore-os4.sh    # 实验结束回 Android
```

**判读顺序**：`ArmCpu: mapGic/wakeRedistributor failed`（GIC 映射）→ `ArmCpu: N timer interrupts`
（核/定时器）→ `ArmCpu: smp step`（从核启动）→ `AppleImage4` / `BootLocker`（kext 阶段）→ 其它 panic。

### 新的 panic（已修，b264）

```
pc  0xfffffff00b900b84  =  _memcpy + 0xb4
     fffffff00b900b7c: str x6, [x3], #0x8
esr 0x96000061（写 + 对齐错）   far 0xfffffffaffc7eab2（末位 b2，非 8 对齐）
lr  (PAC 签名后) 0xfffffff00c43788c = UkeAdvLogger 的消息拷贝调用点
```

内核的 `memcpy` 按 8 字节搬运、**不检查对齐**（arm64 上一般合法，因为我们把 `SCTLR_EL1.A` 打开了才致命）。
调用方是 Advanced Logger 的消息拷贝：目标是 8 对齐的，**源是 msgbuf 里的任意字节偏移**。
把两个 writer 里的 9 处 `memcpy` 全换成 `uke_byte_copy`（volatile 字节循环），并新增
`tools/check-adv-log.py` 自测 9：**这两个文件里出现 `memcpy` 即失败**（两个天然对齐的调用点进白名单）。

**这是同一个教训的第三次**：packed 结构体（b256）→ 字节写被合并（b257）→ memcpy 碰上字节偏移（b263）。
三次都是"假设宽访问无害"。自测 9 是第一个能**在刷机前**发现它的检查。

### 面板里还看到的三件事（新问题，按优先级）

1. **P6 内存几乎耗尽**：`vm_page_find_contiguous: no run of 34 pages` 反复出现、
   `wired count is 43981 / 43984`（只剩 3 页空闲）。kext 加载阶段就这个水位，
   要么是 `kt_fixed_zones`/wired 预留太大，要么是有泄漏；需要对着 sheng 的
   `kt_fixed_zones=120`、`memory-window-high=1`、`gpu-pool=0` 这几条参数比。
2. **APFS 未安装**：`AppleAPFSContainer: Failed to publish profile data (1)`、`IOPAppleAPFS: Error: Failed to open …`
   —— data 分区里还没有可挂载的 macOS 容器，属于"还没走到那步"，不是 bug。
3. **NVRAM 缺失**：`No _nvram_controller` —— 我们的 `ArmDTPlatform` 提供了空 proxy，够启动但拿不到持久 NVRAM。

### 下一轮验收（b264 之后）

## 六、2026-11-18 晚场结果（b263→b268）与两个拦路问题

### 6.1 已经确定解决的

| | 证据 |
|---|---|
| **P1 平台错误风暴**（我们自己的 GICR SGI 帧回读）| b263 起整段日志一次 `platform error` 都没有 |
| **P2 只有 CPU0**（dts 缺 cluster-type）| b264 跑到 `MAC Framework` / `IOService::start` / `CoreAnalyticsLab::start completed` / APFS 挂载尝试 |

| **日志 DMA 分配**（`IOMallocContiguous` 要 4 GiB 以下）| b265 的面板原文 `userdata log transport unavailable: dma buffer` + `vm_page_find_contiguous(num=34, low=1048575) found 0 pages`；b268 换成 `IOBufferMemoryDescriptor` |

### 6.2 问题 A：UFS 控制器是否 32 位（决定日志通道怎么修）

厂商 DT 给出的是：`ufshc iommus = <&apps_smmu 0x60 0x0>`、`qcom,iommu-dma-addr-pool = <0x1000 0xFFFFF000>`——
限制在 **IOVA**，不是物理地址。所以正路是让 SMMU 把高段物理内存映射成低段 IOVA。

但 b268 里我们加的闸门先给出判据：面板上

- `UkeLastLog: userdata log transport attached` → 控制器支持 64 位，走 SMMU/直连都行
- `... unavailable: dma buffer above 4 GiB, controller is 32-bit` → 只支持 32 位，必须给低段缓冲

**低段缓冲的现成做法**：固件预留一小块低段 DRAM（`AllocateAddress`），把地址通过 boot-arg 交给内核
（和它现在交 Advanced Logger 缓冲区 `0xB112E000` 完全一个套路），内核用 `ml_io_map` 映射后直接当 DMA 缓冲用。

### 6.3 问题 B：固件 ASSERT（`ArmCpuDxe CpuExceptionHandlerLib.c(438)`）——今晚的拦路虎

- 现象：面板 `Synchronous Exception at 0x…` + 栈 dump + `ASSERT [ArmCpuDxe] …((BOOLEAN)(0==1))`，
  屏幕上那串值全是 `0xA77xxxxx / 0xB13xxxxx`（固件自己的低段）
- **已经排除**：断电（清 DRAM）后仍然复现 → 不是脏 DRAM 残留；Android 能正常启动 → 分区/持久数据没坏
- **已经排除**：b268 的 4 GiB 闸门已经让内核不再用高段缓冲做 DMA，但 ASSERT 仍两次出现 → 与 DMA 截断**不同因果**
- 这是本 port 的历史问题：b156/b158/b175 出现过同一个 ASSERT（当时归因为写 pram 区）

**下次要拿到的第一个数据**：ASSERT 屏最上面那行 `Synchronous Exception at 0x<ELR>`。
我们的补丁 `Resources/MuPatches/Cpu-Exception-Persist.patch:310` 本来就会打印它，只是拍照时被切掉了。
拿到 ELR 后可以直接对 `Build/ukePkg/DEBUG_CLANGPDB/AARCH64/ArmPkg/Drivers/CpuDxe/CpuDxe/DEBUG/ArmCpuDxe.map`
符号化（ArmCpuDxe 在固件里加载于 `0xAF81B000`，入口 `0xAF81D1AC`，见固件日志）。

**第二个数据**：`UKE_PERSIST_CRASH`（`0xA7605000 + 0x400`）里已经存了 ESR/FAR/ELR/Image，
但固件崩得太早、`UkeBootMemoryDxe` 来不及在下次启动打印它。可行的改法是把这条记录在异常处理里
**直接写进 Advanced Logger 缓冲区**（`0xB112E000`），下次启动的 QR 导出就能读到。

2. 同时做**低段 DMA 窗口**（固件预留 + boot-arg），把日志通道打通
3. 通道通了再回到 P6（内存水位 `wired 43981/43984`）和 APFS
